Mini-Transformer · 멀티헤드 어텐션 다시 쉽게

멀티헤드 어텐션은
"카메라 여러 대로 한 장면 찍기" 입니다

어텐션(Scaled Dot-Product Attention) 하나만 쓰면 한 가지 관점만 보게 됩니다. 멀티헤드는 같은 문장을 여러 대의 카메라(헤드)로 동시에 찍어 각기 다른 관점(의미·구조·위치 등)을 모은 뒤 한 장으로 합치는 장치예요. 아래에서 헤드 수를 직접 바꿔 보며 확인해 봅시다.

1. 무슨 문제 2. 카메라 여러 대 비유 3. 쪼개기(split) 4. 왜 헤드마다 다르게 볼까 5. 직접 해보기 6. 코드 라인별 설명 7. 헷갈리기 쉬운 점 8. 요약

1 어텐션 한 벌로는 부족한 이유 (30초)

이전 문서에서 배운 어텐션(Q·K·V)은 딱 한 번 계산됩니다. 질문 "먹구름이" 와 답 "비가" 의 의미 관련성은 잘 잡아내지만, 동시에 "몇 번째 단어인가", "문장 구조상 무슨 역할인가" 같은 다른 관점은 한 번의 계산에 다 담기 어려워요.

카메라 한 대로는 한 각도만 찍힌다
→ 카메라를 여러 대 두고 각자 찍은 뒤 합치자
🎥노트북 코드 주석 그대로: "한 번에 한 관점만 보지 말고, 여러 '헤드'로 나눠 서로 다른 관점(문법/의미/위치 등)에서 동시에 주목한 뒤 합칩니다. 카메라 여러 대로 같은 장면을 다른 각도에서 찍는 셈."

2 비유: 카메라 여러 대, 나중에 한 장으로

멀티헤드 어텐션이 하는 일은 딱 세 단계입니다. 이전 문서의 도서관 비유(Q=검색어·K=색인·V=내용)에 "카메라 대수" 하나만 추가하면 됩니다.

① 쪼개기

📷 카메라 배치

Q·K·V 전체를 헤드 수(h)만큼 나눠, 각 카메라가 담당할 부분(dₖ차원)을 정합니다.

② 각자 촬영

🔎 헤드별 어텐션

각 헤드가 독립적으로 이전 문서의 어텐션 공식을 그대로 계산합니다. 서로 간섭하지 않아요.

③ 합치기

🖼️ 한 장으로

헤드별 결과를 이어붙이고(merge), 선형변환(wo)으로 한 번 더 섞어 최종 결과를 냅니다.

💡핵심 제약: d_model = h × dₖ. 전체 폭(d_model)은 그대로 두고 카메라 대수(h)를 늘리면 카메라 한 대당 담당 폭(dₖ)은 줄어듭니다. 폭을 나눠 쓰는 거예요.

3 쪼개기(split) — d_model을 헤드로 나누기

실습 노트북의 체크포인트는 d_model=8 로 테스트합니다. 아래에서 헤드 수(h)를 눌러 바꾸면, 헤드 한 개당 차원 dₖ = d_model / h 이 어떻게 달라지는지 보세요.

d_model = 8 (체크포인트 셀과 동일) · 헤드 수 선택

d_model = 8 (전체 폭, 안 바뀜)dₖ = 8 / 4 = 2
📐 텐서 모양으로 보면 (B, S, d_model) → view+transpose → (B, h, S, dₖ). 헤드 축을 앞으로 빼서 헤드별로 완전히 따로 어텐션을 계산할 수 있게 만드는 것뿐, 값 자체는 그대로 재배열됩니다(정보가 사라지지 않음).
🏭실제 학습에 쓰는 진짜 값 (부품⑨ Transformer 기본 하이퍼파라미터, 실제 학습 셀에서도 그대로 사용): d_model=64, num_heads=4 → dₖ = 64 / 4 = 16. 체크포인트(8→4→2)와 똑같은 공식, 숫자만 실전 크기예요.
# split: (B, S, d_model) → (B, h, S, dk)
def split(self, x):
    b, s, _ = x.shape
    return x.view(b, s, self.h, self.dk).transpose(1, 2)   # (B, 헤드, 길이, dk)

4 헤드마다 왜 다르게 볼까?

코드를 보면 wq, wk, wv 는 각각 d_model → d_model 한 덩어리 선형변환입니다. 헤드별로 따로 만든 작은 Linear가 있는 게 아니에요. 대신 이 큰 변환의 출력을 split 으로 조각냅니다.

🧩 그런데 학습이 진행되면, wq(과 wk, wv)의 각 조각(헤드 몫)은 서로 다른 방향으로 값이 조정됩니다. 그 결과 어떤 조각은 우연히 "의미 관련성"에 민감해지고, 다른 조각은 "문장 위치"에 민감해지는 식으로 자연히 역할이 나뉘는 경향이 생깁니다. 누가 정해준 게 아니라 학습이 알아서 다른 관점을 만들어내는 거예요.

아래 5번에서는 이 "관점이 다르다"는 게 실제로 어떤 모습인지, 같은 예시 벡터를 두 헤드로 쪼개 직접 계산해 보여드립니다.

5 직접 해보기 — 헤드 2개, 서로 다른 관점

이전 문서 6번 데모에서 쓴 질문 "하늘에·먹구름이·보이면·뭐가·생각나" / 답 "비가·올·것·같아" 의 4차원 예시 벡터를 그대로 가져와, 앞 2차원 = 헤드 A(날씨현상·하늘배경), 뒤 2차원 = 헤드 B(질문구조·서술) 로 쪼갠 뒤, 진짜 scaled_dot_product_attention 공식으로 헤드별 어텐션을 각각 계산합니다.

② 비가 의 헤드 A(날씨·배경) 주목 비율

비가 의 헤드 B(구조·서술) 주목 비율

👀 "비가"와 "같아"를 번갈아 눌러 보세요 — 뚜렷한 쪽이 서로 바뀝니다.
고른 답 단어헤드 A (날씨·배경)헤드 B (구조·서술)
비가먹구름이 96% — 콕 집음하늘에 39% · 먹구름이 43% — 둘을 비슷하게
같아16~24%로 거의 평평생각나 66% — 콕 집음
같은 문장·같은 함수인데도 "비가"는 헤드 A가, "같아"는 헤드 B가 말을 겁니다. 헤드 A는 앞 2차원(날씨·배경)만, 헤드 B는 뒤 2차원(구조·서술)만 보기 때문이죠. 이게 바로 "카메라 여러 대"의 값어치입니다 — 한 대만 뒀다면 둘 중 하나는 놓쳤을 테니까요. ("올"과 "것"도 눌러 보세요. 둘 다 헤드 B가 생각나 쪽을 봅니다.)

6 코드 라인별 설명

노트북 hands-on/example-explain.ipynb 셀 18의 MultiHeadAttention 클래스입니다. 전체를 ①~⑫ 열두 덩어리로 쪼개, 각 줄마다 ① 함수 자체가 하는 일과 ② 우리 예제에서 실제로 나온 값을 나란히 봅니다.

① class MultiHeadAttention(nn.Module):
①     def __init__(self, d_model, num_heads, dropout=0.1):
①         super().__init__()
②         self.h, self.dk = num_heads, d_model // num_heads
③         self.wq = nn.Linear(d_model, d_model); self.wk = nn.Linear(d_model, d_model)
③         self.wv = nn.Linear(d_model, d_model); self.wo = nn.Linear(d_model, d_model)
④         self.dropout = nn.Dropout(dropout)
④         self.last_attn_weights = None

⑤     def split(self, x):
⑤         b, s, _ = x.shape
⑥         return x.view(b, s, self.h, self.dk).transpose(1, 2)

⑦     def merge(self, x):
⑦         b, _, s, _ = x.shape
⑦         return x.transpose(1, 2).contiguous().view(b, s, self.h * self.dk)

⑧     def forward(self, q, k, v, mask=None):
⑨         q, k, v = self.split(self.wq(q)), self.split(self.wk(k)), self.split(self.wv(v))
⑩         ctx, attn = scaled_dot_product_attention(q, k, v, mask, self.dropout)
⑪         self.last_attn_weights = attn.detach()
⑫         return self.wo(self.merge(ctx))
🧾 아래 모든 숫자는 실제로 학습시킨 모델에서 뽑았습니다. torch.manual_seed(42)로 400에폭 학습(loss 0.0035) 후, 질문 "하늘에 먹구름이 보이면 뭐가 생각나"를 넣어 답 "비가 올 것 같아"를 생성한 뒤 마지막 디코더 층의 크로스 어텐션에서 측정한 값입니다. 5번 섹션의 데모와는 출처가 다릅니다 — 5번은 손으로 만든 4차원 예시 벡터, 여기는 학습으로 얻은 16차원 실제 벡터입니다. 두 곳의 비율이 비슷해 보여도 우연입니다. (파이토치 버전이 다르면 소수점은 달라집니다)
🔢 헤드 번호를 두 가지로 세는 점만 미리 짚어 둡니다. 코드와 표는 0부터(헤드0·헤드1·헤드2·헤드3) 세고, 그림은 1부터(헤드 1~4) 셉니다. 파이썬 인덱스가 0부터 시작하기 때문입니다. q[0,0,1] 은 첫 번째 헤드이고, 그림에서는 "헤드 1"로 적힌 그 조각입니다.

🔀 왜 transpose 를 따로 하나요? 처음부터 view(b, h, s, dk) 로 쓰면 안 될까요?
안 됩니다. 그런데 모양은 똑같이 나오고 에러도 안 나서 더 위험합니다 — 값만 조용히 뒤섞입니다. view 는 숫자를 일렬로 늘어놓은 순서대로 새 칸에 채우기 때문에, 한 단어의 64칸이 아니라 여러 단어의 값이 한 헤드에 섞여 들어갑니다. 쪼개는 순서는 반드시 "단어별로 4×16으로 자른 뒤, 헤드축을 앞으로" 여야 합니다.

⑦ transpose(1,2).contiguous().view(b, s, h*dk)

💥 contiguous() 는 빼도 되는 최적화처럼 보이지만, view 를 쓰는 한 필수입니다. transpose 는 값을 실제로 옮기지 않고 "보는 순서"만 바꿉니다. 그 상태로 view 를 부르면 이렇게 실패합니다. 
RuntimeError: view size is not compatible with input tensor's size and stride
    (at least one dimension spans across two contiguous subspaces).
    Use .reshape(...) instead.
실측: transpose(1,2) 직후 is_contiguous = False → contiguous() 후 True → view 성공.
에러 메시지가 알려주듯 방법은 두 가지입니다. ① contiguous().view(...) ② reshape(...) — 둘의 결과는 완전히 같고, 이 경우 reshape 도 내부에서 똑같이 복사합니다. 즉 contiguous() 는 "view 를 쓰기로 정했으니 필요한 것"이지, 공짜로 복사를 없애 주는 최적화가 아닙니다.

🔁 "헤드가 4개니 for 문으로 4번 돌아야 하지 않나요?" — 반복문이 한 줄도 없습니다. 어텐션 함수는 뒤쪽 두 축만 보고 계산하고, 앞의 (1, 4) 는 배치 차원으로 자동 반복됩니다. 실제로 헤드별로 따로 계산한 결과와 한 번에 계산한 결과를 비교하면 오차 0.0으로 완전히 같습니다.
두 가지만 짚어 둡니다. ① 파이썬 코드에 for 가 없다는 뜻이고, 계산량이 4벌인 사실은 그대로입니다. ② 헤드는 서로 완전히 독립입니다 — 헤드0의 q 값만 흔들어 보면 헤드0의 결과만 변하고 나머지 세 헤드의 변화량은 정확히 0이었습니다 (여러 방식으로 흔들어 봐도 모두 0).

✂️ detach() 는 값을 복사하는 게 아닙니다. 떼어낸 뒤에도 원본과 같은 메모리를 공유합니다 — 줄어드는 것은 딸려 있던 계산 기록(계산그래프)이에요. 떼지 않고 보관하면 이 텐서에 매달린 상류 계산 기록이 함께 살아남습니다(실측으로 확인). 단 backward() 를 부르면 저장된 중간값은 해제되므로, 문제가 되는 쪽은 주로 no_grad 없이 추론만 반복하는 경우입니다.
이 값은 학습에 쓰이지 않습니다 — 오직 노트북 히트맵과 5번 데모를 위한 구경용이에요.
🌡️ 히트맵은 반드시 model.eval() 에서 그리세요. 이 줄은 드롭아웃을 통과한 뒤의 값을 저장합니다. 그래서 train() 모드에서 꺼내 보면 행의 합이 1이 아닙니다 — 실측하니 행 합이 1.1111 처럼 1을 넘거나 1보다 작은 값으로 흔들리고, 120칸(=4×6×5) 중 10여 칸이 정확히 0이었습니다. (0이 되는 칸의 개수는 무작위라 실행마다 달라집니다. 시드를 바꿔 재보니 15·10·13·16칸이었습니다.)
eval() 에서는 드롭아웃이 통과하므로 모든 행의 합이 정확히 1.0 입니다. ⑩ 표의 비율들도 그래서 합이 100%가 됩니다.

7 헷갈리기 쉬운 점

⚖️헤드를 늘리면 무조건 좋아지나? 아니요. d_model이 고정이면 헤드(h)를 늘릴수록 헤드당 폭(dₖ)이 줄어듭니다. 헤드가 너무 많아지면 한 헤드가 담을 수 있는 정보가 너무 작아져 오히려 표현력이 떨어질 수 있어요. 이 노트북은 d_model=64에 num_heads=4(dₖ=16)로 균형을 잡았습니다.
🧪체크포인트가 실제로 확인하는 것: MultiHeadAttention(8, 4, 0.0) 에 모양 (1,3,8) 짜리 Q,K,V를 넣으면 출력도 그대로 (1,3,8) 이어야 합니다(차원 보존). 헤드로 쪼개고 다시 합치는 과정에서 모양이 안 틀어지는지를 검증하는 거예요 — 값이 아니라 "배관이 안 새는지" 확인입니다.
🔁self든 cross든 똑같이 동작합니다. 이전 문서 8번에서 본 것처럼, MultiHeadAttention도 self_attn(x,x,x) 로 부르면 셀프어텐션, cross_attn(x, enc, enc) 로 부르면 크로스어텐션이 됩니다. 헤드로 쪼개는 로직은 어느 쪽이든 동일해요.
