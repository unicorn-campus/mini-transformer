## 1. 배경과 목표

### 1.1 배경

기존 워밍업 실습 `hands-on/mini-transformer/` 는 "하늘에 먹구름이 보이면 뭐가 생각나 → 비가 올 것 같아"
6쌍으로 미니 트랜스포머 전체를 체험시키는 교재임. 학습자는 어텐션·마스킹·위치인코딩을 이미 학습한 상태임.

이 상태의 학습자에게 남은 질문은 **"왜 트랜스포머가 나왔나"** 임. 이 질문은 트랜스포머만 봐서는 답이 안 나옴.
어텐션이 없던 시절의 구조를 **같은 데이터로 직접 돌려 봐야** 답이 나옴.

### 1.2 목표

**같은 문제를 다른 구조로 풀어, 구조의 차이를 실행 결과로 체감시키는 GRU 실습 프로그램 개발.**

설계 원칙은 **통제변인 하나만 바꾼다** 임. 데이터·단어장·시드·학습률·에폭 수를 전부 동일하게 고정하고
아키텍처만 교체함. 그래야 학습자가 보는 모든 출력 차이가 100% "구조 때문"으로 귀속됨.

### 1.3 비목표 (하지 않는 것)

- GRU 성능 개선·튜닝 — 6쌍 암기 문제이므로 성능은 논점이 아님
- 다층 GRU·양방향 GRU·LSTM 비교 — 게이트 하나에 집중함
- 새로운 데이터셋 도입 — 기존 6쌍을 그대로 씀 (§3.6 판정 근거)

#### (c) 사라지는 트랜스포머 부품 6종 — **이것이 가장 강력한 교육 자산**

`mini_transformer.py` 의 부품 10개 중 6개가 사라짐. 각 부품의 자리에 **왜 필요 없어졌는지를 주석으로 남김**.

| 사라지는 부품 | 주석에 쓸 이유 |
|--------------|---------------|
| `PositionalEncoding` | 순서대로 한 개씩 넣으므로 순서 정보가 **구조에 이미 들어 있음** |
| `scaled_dot_product_attention` | 어느 단어를 볼지 고르지 않음. 무조건 **직전 은닉 상태 하나**만 봄 |
| `MultiHeadAttention` | 위와 동일 |
| `PositionwiseFeedForward` | 게이트 계산 자체가 비선형 변환 역할을 겸함 |
| `make_padding_mask` · `make_causal_mask` · `make_decoder_mask` | 미래를 가릴 필요가 없음 — **아직 계산조차 안 했으므로 볼 수가 없음** |
| `EncoderLayer` · `DecoderLayer` (LayerNorm·잔차) | 층이 1개라 쌓을 게 없고, 게이트가 값의 크기를 스스로 억제함 |

→ `mini_gru.py` 의 3단계 부품 배너는 **①~④** 임(트랜스포머는 ①~⑩). 배너 번호 자체가 메시지임.

### 3.3 GRU 셀 — 직접 구현 + `nn.GRUCell` 대조 검증

**결정: 게이트 수식을 손으로 쓰고, `nn.GRUCell` 과 값이 일치하는지 셀프테스트로 검증함.**

근거:
- 직접 구현만 하면 "내가 쓴 수식이 진짜 GRU 인가?"를 학습자가 확인할 방법이 없음 — 입문자의 최대 불안 요소
- `nn.GRU` 만 쓰면 게이트가 블랙박스가 됨. 더 결정적으로 **게이트 값을 꺼내 시각화할 수 없음**
  (`nn.GRU` 는 게이트를 반환하지 않음) → §4.3 게이트 관찰이 원천적으로 불가능해짐
- 대조 검증의 추가 비용은 약 10줄이며, 기존 `if __name__` 블록의 `assert` + `print("✅ … OK")`
  패턴에 완전히 같은 관례로 흡수됨

구현 형태는 **융합 Linear 2개 + `chunk(3, dim=-1)`** 임. Linear 6개를 따로 두는 것과 값이 완전히 같고
행렬곱이 2번으로 줄어 빠름.

```python
xr, xz, xn = self.x2h(x).chunk(3, dim=-1)   # 새 입력을 세 칸(r·z·n)으로
hr, hz, hn = self.h2h(h).chunk(3, dim=-1)   # 기존 기억을 세 칸으로
r = torch.sigmoid(xr + hr)          # 리셋 게이트 (0~1)
z = torch.sigmoid(xz + hz)          # 갱신 게이트 (0~1)
n = torch.tanh(xn + r * hn)         # 후보 (-1~1). r 은 h2h 통과 '후' 에 곱함
return (1 - z) * n + z * h, r, z    # 새 기억, 그리고 시각화용 게이트 2개
```

**3대 함정** (전부 에러 없이 돌아가므로 assert 로만 잡힘):

| 함정 | 잘못된 코드 | 결과 | 잡는 장치 |
|------|-----------|------|----------|
| `chunk` 순서 | `(z, r, n)` 등으로 바꿈 | `nn.GRUCell` 과 값 불일치 | L1-3 `allclose` |
| `r` 곱하는 자리 | `tanh(xn + self.h2h(r * h))` | 학습은 되지만 PyTorch 와 다른 변종 | L1-3 `allclose` |
| `z` 방향 | `z * n + (1 - z) * h` | 학습은 되지만 **게이트 해석이 전부 반대** | L1-4 강제 포화 테스트 |

`forward` 가 `(h_new, r, z)` 3개를 반환하는 이유: `MultiHeadAttention.last_attn_weights` 처럼 속성에
보관하면 스텝마다 값이 덮어써짐. 반환값으로 넘겨 인코더가 `torch.stack` 으로 모으는 편이 데이터 흐름이
눈에 보임.

### 3.4 하이퍼파라미터 — 통제변인 고정

| 항목 | GRU | 트랜스포머 | 판정 근거 |
|------|-----|-----------|----------|
| `emb_dim` / `hidden_size` | 64 / 64 | `d_model=64` | 동일 고정. 가중치 공유 조건(`hidden == emb`)도 자동 충족 |
| `num_layers` | **1** | 2 | 5토큰 문장에 층을 쌓을 이유가 없고, 다층 GRU 는 `h` 리스트 관리로 코드가 흐려짐 |
| `dropout` | 0.1 (임베딩 출력·출력층 직전) | 0.1 | 게이트 내부에는 넣지 않음 — 순환 dropout 은 별도 주제 |
| `lr` / 옵티마이저 | 3e-4 / Adam | 동일 | 동일 |
| 에폭 | 400 | 400 | 동일 |
| 시드 | `torch.manual_seed(42)` | 42 | 동일 |
| 손실 | `CrossEntropyLoss(ignore_index=pad)` | 동일 | 동일 |
| 티처 포싱 | `dec_in=tgt[:,:-1]`, `dec_tgt=tgt[:,1:]` | 동일 | 동일 |
| 가중치 공유 | 적용 (`out.weight = dec.emb.weight`, `bias=False`) | 적용 | 아래 표 참조 |
| `answer` 생성 상한 | `max_len=20` | 20 | 동일 |

**가중치 공유(weight tying) 채택 — 프로토타입 측정 근거**

| 설정 | 파라미터 | 최종 loss | 정답 |
|------|---------|----------|------|
| tying 없음 | 65,426 | 0.0934 | 6/6 |
| **tying 적용** | **64,256** | **0.0102** | **6/6** |

파라미터가 줄었는데 loss 가 9배 개선됨. 트랜스포머와 동일한 관례를 유지하므로
"같은 기법이 RNN 에도 그대로 통한다"는 메시지가 덤으로 붙음.

**디코더 context 전달 방식 — 매 스텝 concat 채택**

`GRUDecoder` 입력 = `[답 임베딩 64 ; context 64] = 128`.

`context` 를 `h0` 초기화에만 쓰는 대안이 더 단순하지만 채택하지 않음. 스텝이 진행될수록 `context` 가
희석되어 **"병목"이 "망각"으로 흐려짐**. 매 스텝 concat 이면 "매 스텝 같은 요약 한 장만 본다"가
크로스어텐션이 빠진 자리에 정확히 대응함.

**파라미터 예상 64,256개** (트랜스포머 235,520개의 약 27%). 내역:

```
src_emb  (14, 64)            896
tgt_emb  (18, 64)          1,152   ← 출력층과 공유되어 out.weight 가 따로 없음
enc.x2h  (192,  64)+bias  12,480
enc.h2h  (192,  64)+bias  12,480
dec.x2h  (192, 128)+bias  24,768   ← 입력이 [임베딩 64 ; context 64] = 128 이라 2배
dec.h2h  (192,  64)+bias  12,480
──────────────────────────────────
합계                      64,256
```

> ⚠️ 위 표의 loss·파라미터 수는 **프로토타입 측정값**임. 구현체의 변수명·초기화 순서가 달라지면 값이
> 바뀌므로, 주석과 문서에 박기 전에 **첫 실행 로그의 실제 출력값으로 갱신**해야 함 (§6.3 완료조건).

### 3.5 체크포인트 스키마

```python
torch.save({
    "format_version": 1,
    "config": {"emb_dim": 64, "hidden_size": 64},
    "model_state": model.state_dict(),
    "src_vocab": src_vocab,
    "tgt_vocab": tgt_vocab,
    "final_loss": train_loss,
    "eval_loss": eval_loss,
    "token_acc": acc,
}, CKPT_PATH)
```

- **`max_len` 키 제거**: 트랜스포머가 이 키를 저장한 유일한 이유는 위치인코딩 버퍼 모양을 맞추기 위함이었음.
  GRU 는 길이에 따라 모양이 바뀌는 파라미터가 하나도 없음. 이 키를 남겨두면 "RNN 도 길이 제한이 있다"는
  오해를 심음. **키의 소멸 자체가 교육 포인트**이므로 `load_model()` 주석에 명시함
- `Vocab` 객체 저장 + `weights_only=False` 는 기존 관례 승계 (두 실습의 체크포인트 스키마 대조 용이).
  기존 코드가 이미 `weights_only=False` 를 명시하므로 torch 2.6+ 기본값 변경에 영향받지 않음
- `format_version` · `config` 추가로 EC-07(설정 불일치) · EC-08(포맷 불일치)을 친절한 에러로 전환

### 3.6 실습 과제 — 동일 6쌍 유지

| 안 | 장점 | 단점 | 판정 |
|----|------|------|------|
| **A. 동일 6쌍 seq2seq** | 통제변인 완벽. loss·파라미터 수·답을 1:1 대조. `Vocab`·`build_batches` 100% 재사용. 학습자가 이미 데이터를 외운 상태라 인지 부하 0 | 질문이 5토큰뿐이라 "긴 문맥 손실"이 데이터만으로는 안 드러남 | **채택** |
| B. 별도 과제 (문자 카운팅·괄호 짝) | 순차성·상태 유지가 극적으로 드러남 | 데이터·단어장·평가 방식이 전부 새로워짐 → 트랜스포머와 비교 불가로 실습 목적 상실. 코드량 +40% | 기각 |
| C. 6쌍 + 긴 문장 추가 | 병목이 데이터로 드러남 | 문장 길이가 달라지면 인코더에 `<pad>` 가 들어가 packed sequence 처리 필요 → 난이도 급상승 | 기각 |

**A 의 단점은 데이터가 아니라 추론 시점 실험으로 해결함.** 학습은 6쌍 그대로 하고, `reasoning.py` 에서
질문에 군더더기 단어를 붙여 병목을 드러냄(§4.3 8·9단계). 학습 코드를 전혀 오염시키지 않고,
배치 크기 1이므로 패딩 문제도 발생하지 않음.

## 4. 교육 설계

### 4.1 학습 목표

실습을 마친 학습자는 다음을 할 수 있음.

1. GRU 셀 코드 4줄에서 리셋 게이트·갱신 게이트·후보·최종 은닉 상태가 각각 어느 줄인지 지목하고,
   `z` 가 0에 가까울 때와 1에 가까울 때 은닉 상태가 어떻게 달라지는지 한 문장으로 설명함
2. `gate_heatmap.png` 와 콘솔 게이트 표에서 **(첫 토큰을 뺀) 갱신 게이트 최저 토큰**을 찾아
   그 토큰이 기억을 가장 크게 바꾼 자리라고 설명하고, **첫 토큰을 왜 빼야 하는지**
   (백지 `h=0` 에서 시작하므로 원래 `z` 가 낮음) 함께 설명함 — 부록.1 ② 참조
3. GRU 디코더가 질문 원문이 아니라 **64칸 요약 벡터 하나**만 받는다는 사실을 코드에서 지목하고,
   실행 결과(군더더기 삽입 → 오답)를 근거로 정보 병목을 설명함
4. 같은 데이터·같은 hidden 크기에서 파라미터 수와 계산 방식(순차 `for` 루프 vs 한 번의 행렬 연산)을
   비교해, 트랜스포머가 어텐션과 병렬 처리를 도입한 이유를 두 문장으로 설명함
5. 함정 3종(은닉 초기화 누락 / `r` 곱하는 자리 / `z` 방향) 중 하나가 심긴 코드를 받아 5분 내 수정함

### 4.2 핵심 개념 비유

기존 톤(멀티헤드="카메라 4대", FFN="각자 책상에서 혼자 곱씹는 단계", 학습="눈 감고 다트 던지기")과
결이 맞도록 **사무실·시험장 계열**로 통일함.

| 개념 | 비유 | 왜 이 비유인가 |
|------|------|---------------|
| 은닉 상태 | **회의록 한 장** — 발언이 들어올 때마다 새 종이를 꺼내지 않고 있던 그 한 장을 고쳐 씀 | GRU 의 본질은 "고정 크기 벡터 하나를 계속 덮어쓴다". '노트'가 아니라 '한 장'이라고 못 박아야 뒤에 다룰 정보 병목이 비유 안에서 예고됨 |
| 갱신 게이트 `z` | **온수·냉수가 하나로 붙은 수도 레버** — 두 쪽 비율의 합이 언제나 1 | `h' = (1-z)*n + z*h` 의 핵심은 "가중 평균이며 가중치 합이 1". 다이얼 2개(독립)로 비유하면 LSTM(입력·망각 게이트 분리)과 혼동됨 |
| 리셋 게이트 `r` | **초안 쓸 때만 잠깐 덮어 두는 지난 회의록** — 찢는 게 아님 | 입문자 최대 오해가 "리셋 = 기억 삭제". 실제로 `r` 은 후보 `n` 계산에만 개입하고 최종 `z*h` 항에는 손대지 않음 |
| 전체 구조 | **이어달리기 배턴** — 디코더는 질문지를 다시 볼 수 없고 앞 주자가 넘긴 요약 한 장만 들고 뜀 | 기존 "답안지 뒷장은 못 보고 문제지는 곁눈질하는 수험생"과 정확히 짝을 이룸 — **곁눈질을 못 하게 만든 버전** |
| 학습 | **다트, 그런데 한 발씩** — 트랜스포머는 6발을 동시에, GRU 는 1발이 꽂힌 뒤에야 다음 발 | 기존 다트 비유를 승계하며 "병렬 불가"라는 유일한 구조적 약점을 한 문장에 담음 |

### 4.4 대조 학습 활동 (강의 운영용)

| 깨달음 | 활동 | 지시 | 성공 판정 |
|--------|------|------|----------|
| 디코더가 질문을 다시 못 본다 | 코드 지목 게임 | GRU 답 생성 루프와 트랜스포머 `answer()` 를 나란히 띄우고, 트랜스포머에는 있고 GRU 에는 **없는 인자**를 찾게 함 | 3분 내 `decode_step(tgt, enc, ...)` 의 `enc` 를 지목 |
| 요약 벡터 한 개는 결국 새어 나간다 | 8단계 실행 | 군더더기 반복 횟수 0/3/5/10 에서 몇 번째에 처음 틀리는지 기록 | 오답 재현 + "회의록 한 장" 비유로 설명 |

| 트랜스포머는 크기가 아니라 병렬성을 산 것 | 대조표 채우기 | 두 실습 콘솔 출력에서 숫자만 옮겨 적기 | 표 완성 + "왜 더 큰 모델이 이겼나"에 답 |

| 파라미터 | 235,520 | 64,256 | GRU 가 약 3.7배 가벼움 |
| 질문 1문장 읽는 방식 | 행렬 연산 1회(전 단어 동시) | `for` 루프 5회(한 단어씩) | GPU 병렬화 가능 여부 |
| 디코더가 질문을 보는 방법 | 매 스텝 크로스어텐션 | 요약 벡터 64칸 1개 | 정보 병목 |
| 단어 간 거리 | 어디든 1홉 | 최대 문장 길이만큼 | 장거리 의존성 |
| 순서 정보 | 위치 인코딩(sin·cos) | 읽는 순서 자체 | **GRU 는 위치 인코딩이 필요 없음** |
| 관찰 가능한 내부값 | 어텐션 가중치 | 리셋·갱신 게이트, 은닉 궤적 | 보이는 것이 다름 |
| 뒤에 군더더기 10개 | 정답 유지 | 오답 | 요약 한 장이 먼저 무너짐 |

> 대조표에서 **"GRU 는 위치 인코딩이 필요 없다"** 칸을 반드시 남길 것. 트랜스포머 실습에서 가장 어려웠던
> 부품이 GRU 에서는 **아예 사라진다**는 사실이 "왜 그 부품이 있었나"를 역으로 이해시키는 가장 강력한 순간임.

### 4.5 함정 목록 (인라인 주석 완성 문장)

| # | 함정 | 주석 문장 |
|---|------|----------|
| ① | 은닉 초기화 누락 / shape 오류 | `⚠️ 문장을 새로 읽을 때마다 은닉 상태를 0으로 다시 만들어야 합니다. 또 (배치, 64) 가 아니라 (64,) 로 만들면 에러 없이 브로드캐스팅되어 6문장이 '같은 회의록 한 장'을 나눠 쓰게 됩니다 — 조용히 틀리는 가장 무서운 실수입니다.` |
| ② | `r` 곱하는 자리 | `⚠️ r 은 은닉 상태에 바로 곱하는 게 아니라 '변환한 뒤' 에 곱합니다. 맞음: tanh(xn + r * hn) / 틀림: tanh(xn + h2h(r * h)). 두 줄 다 에러 없이 학습되지만 nn.GRUCell 과 값이 달라집니다.` |
| ③ | `z` 방향 뒤집기 | `⚠️ h_new = (1 - z) * n + z * h 입니다. z 는 '새것을 받을 비율'이 아니라 '옛 기억을 지킬 비율'입니다(PyTorch 관례). 이름이 '갱신 게이트'라서 반대로 외우기 쉽습니다. 뒤집어도 학습은 되지만 게이트 해석이 정반대가 되어 결론이 거짓이 됩니다.` |
| ④ | 시퀀스 축 순서 | `⚠️ 우리 텐서는 (배치, 시간, 칸) 순서입니다. t 번째 단어는 e[:, t] 이지 e[t] 가 아닙니다. e[t] 를 쓰면 shape 만 맞고 의미가 완전히 망가집니다.` |
| ⑤ | 마지막 은닉 vs 전체 출력 | `⚠️ 인코더가 돌려주는 것은 '마지막 은닉 상태 1개' 이고, 디코더가 돌려주는 것은 '모든 시점의 출력' 입니다. 인코더에서 전체 시점을 모아 넘기고 싶어지면 잠깐 멈추세요 — 그것을 하는 순간 여러분은 어텐션을 다시 발명하고 있는 것입니다.` |
| ⑥ | `detach()` 누락 | `⚠️ 은닉 상태를 다음 에폭으로 이어서 쓰면 계산 그래프가 이어져 "backward through the graph a second time" 에러가 납니다. 우리 실습은 매 에폭 0으로 새로 시작하므로 이 문제가 없습니다 — 왜 없는지 설명할 수 있어야 합니다.` |
| ⑦ | `zero_grad()` 누락 | `⚠️ opt.zero_grad() 를 빼면 지난 기울기가 계속 더해집니다. GRU 는 for 루프로 같은 셀을 여러 번 지나므로 기울기가 쌓이는 속도가 트랜스포머보다 빠릅니다.` |
| ⑧ | `<pad>` 가 은닉을 오염 | `⚠️ CrossEntropyLoss(ignore_index=pad_id) 는 '점수 계산'에서만 <pad> 를 빼 줍니다. 은닉 상태는 <pad> 를 읽는 동안에도 계속 바뀝니다 — 손실에서 뺐다고 기억이 깨끗한 게 아닙니다.` |
| ⑨ | `eval()`·`no_grad()` 누락 | `⚠️ model.eval() 을 빼면 드롭아웃이 켜진 채로 답을 만들어 같은 질문에 매번 다른 답이 나옵니다. 게이트 값도 흔들려 히트맵을 신뢰할 수 없게 됩니다.` |
| ⑩ | 게이트에 `tanh` 사용 | `⚠️ 게이트(r, z)는 반드시 sigmoid(0~1, '비율')이고 후보(n)는 tanh(-1~1, '값')입니다. 게이트에 tanh 를 쓰면 '-30% 를 기억한다' 같은 말이 되어 학습이 요동칩니다.` |

### 5.1 주석 작성 규약

**정량 기준: 설명이 전체 줄 수의 50% 이상.** 기존 `mini_transformer.py` 534줄 중 실행 코드가
절반 이하이고 나머지가 섹션 배너·docstring·인라인 주석인 밀도를 그대로 승계함.

여기서 "설명"은 **주석·docstring + 학습자용 설명 `print`** 를 뜻함. `print("⭐ 회의록은 한 장뿐입니다…")`
같은 줄은 문법상 코드지만 학습자가 읽는 설명문 자체이며, 같은 내용을 주석으로 한 번 더 쓰는 것은
오히려 코드를 나쁘게 만듦. 판정을 흐리지 않기 위해 **두 수치를 모두 기록**함.

**실측 결과**

| 파일 | 전체 | 주석·docstring | 설명 `print` | 순수 코드 | 주석만 | **설명 합계** |
|------|-----:|---------------:|-------------:|----------:|-------:|-------------:|
| `mini_gru.py` | 622 | 335 | 12 | 187 | 53.9% | **55.8%** |
| `training.py` | 214 | 105 | 15 | 72 | 49.1% | **56.1%** |
| `reasoning.py` | 289 | 117 | 43 | 97 | 40.5% | **55.4%** |

`reasoning.py` 는 주석만 세면 40.5% 로 기준 미달임. 이 파일은 성격상 학습자에게 결론을 **출력으로**
보여 주는 것이 본업이어서(대조 실험 3종의 해설이 전부 `print`) 설명이 `print` 쪽에 실림.
세 파일 모두 설명 합계로는 55% 이상임.

#### 5계층 주석 구조

| 계층 | 형식 | 담을 내용 |
|------|------|----------|
| **① 모듈 docstring** | `[한 줄 요약] {비유}` → `하는 일` 단계 목록 → `실행:` 명령 | 파일 전체가 무엇인지. 기존 3파일과 동일 형식 |
| **② 섹션 배너** | `# ─────…`(77자) + `3단계 부품 ①: 제목` + `# 🖼️ 그림:` 링크 | 부품 단위 구획. 이미지 링크가 붙는 자리 |
| **③ 클래스·함수 docstring** | 비유 1문장 → 역할 → 입출력 shape → 학습 파라미터 유무 | "이 부품이 무엇에 해당하나" |
| **④ 인라인 주석** | 코드 오른쪽 정렬 | **거의 모든 실행 라인**에 붙임. 그 줄이 무엇을 하는지 + 실측 shape/값 |
| **⑤ 함정 주석** | `# ⚠️` 로 시작하는 블록 주석 | §4.5 10건. 잘못된 코드와 그 결과를 함께 씀 |

#### 필수 준수 항목

- **언어**: 주석·docstring 전부 **한글 존대체**("~합니다"). 영어는 식별자와 기술 용어(weight tying,

- **실측값 병기**: 텐서 shape·파라미터 수·게이트 값 범위를 주석에 숫자로 박음
  (예: `# 실측 shape: (6, 5)`, `# 실측: r 0.51~0.68`). ⚠️ 첫 실행 로그의 실제 값이어야 함 — 추정값 금지
- **비유 연결**: 각 부품 docstring 첫 줄은 §4.2 비유로 시작함. 코드를 읽다가 비유가 떠오르게 만드는 것이 목적

- **번호 주석**: 학습 루프의 3줄에는 기존처럼 `# (1) 예측` `# (2) 정답과 비교` `# (3) 가중치 수정` 를 붙임

| **L1** | 부품 단위 | `python mini_gru.py` | `✅` 7줄 전부 + 종료코드 0 | < 3초 |
| **L2** | 학습 스크립트 | `python training.py` | `✅` 5줄 + `💾 저장 완료` | < 30초 |
| **L3** | 추론 스크립트 | `python reasoning.py` | `✅` 5줄 + `🖼️` + `🔖 회귀 지문` | < 5초 |
| **L4** | E2E 시나리오 | 시나리오 E1~E6 | 시나리오별 기대 동작 일치 | < 3분 |

**설계 원칙 4가지**

- `assert` 는 **죽이는 것이 목적**임. 학습자가 잘못된 결과를 보고 잘못 배우는 것보다 명확한 메시지로 멈추는 게 나음
- **정확값 `assert` 는 정수(카운트·shape)에만**. 부동소수는 부등호 / `allclose` / 집합 포함으로
- **행위 검증 > 수치 검증**: `loss < 0.35` 보다 `토큰 정확도 == 1.0` 이 플랫폼 안정적임(argmax 는 이산값)
- `assert` 메시지는 **학습자를 향한 안내문**임. 원인과 조치를 한 줄에 담음

#### L1 — 부품 셀프테스트 7항목

| # | 검증 항목 | 핵심 assert |
|---|----------|------------|
| 1 | 사전 | `_sv.pad_id == 0 and _tv.sos_id == 1`, `len(_sv) == 14 and len(_tv) == 18` |
| 2 | 게이트 범위·shape | 입력을 10배로 키워 포화시킨 뒤 `0 ≤ r,z ≤ 1`, `-1 ≤ n ≤ 1`, `h.shape == (4, 7)` |
| 3 | `nn.GRUCell` 일치 | 가중치 복사 후 `allclose(atol=1e-6)`. 5스텝 롤아웃은 `atol=1e-5` |
| 4 | 게이트 방향 | `z` 를 강제 포화시켜 `z≈1 → h' == h`, `z≈0 → h' == n` 양방향 확인 |
| 5 | 은닉 유계성 | 입력 ×50 으로 20스텝 돌려도 `|h| ≤ 1 + 1e-6` (볼록결합이라 수학적으로 보장됨) |
| 6 | 순차 처리 인과성 | 마지막 토큰만 바꿔 `torch.equal(hs1[:, :4], hs2[:, :4])` — 미래 정보 누출 검출 |
| 7 | `nn.GRU` 시퀀스 일치 | 전체 시퀀스 `allclose(atol=1e-5)` — 루프 방향·`h0=0` 검증 |

**허용 오차 근거**: 두 구현은 동일 수식이나 연산 융합 방식이 다름(PyTorch 는 융합 커널, 직접 구현은
`Linear` 개별 호출). float32 에서 한 스텝 누적 오차가 `~1e-7` 규모이므로 1스텝 `1e-6` / 5스텝 `1e-5` /
20스텝 이상 `1e-4` 로 잡음. `1e-8` 로 조이면 정상 구현도 플랫폼에 따라 실패함.

#### L2 — 3단 수렴 게이트

기존 실습은 `assert loss.item() < 0.5` 단일 게이트였음. 드롭아웃이 켜진 학습 loss 에는 바닥(floor)이
생겨 임계값을 느슨하게 잡아야 하므로 미수렴 검출력이 약함. GRU 실습은 3단으로 강화함.

| 게이트 | 기준 | 성격 |
|--------|------|------|
| ① 학습 loss (드롭아웃 켜짐) | `< 0.35` **(잠정)** | 관측 게이트 |
| ② 평가 loss (`model.eval()`) | `< 0.10` **(잠정)** | 드롭아웃 floor 가 없어 3배 조일 수 있음 |
| ③ 상대 감소율 | `< 시작 loss × 0.15` | 플랫폼·버전 무관 |
| ④ **토큰 정확도** | `== 1.0` | **실질 게이트**. argmax 이산 판정이라 부동소수 편차에 면역 |

**추가 조기 검출**: 정답 정렬은 `dec_in[:, 1:] == dec_tgt[:, :-1]` 로 **정확히** 검사함(오차 없는 등호).
1에폭 loss 는 폭발 여부만 넉넉히(`1.0 < L < 8.0`) 확인함 — 가중치 공유 때문에 이론값 `ln(18) = 2.890`
보다 높게 출발하는 것이 정상이며, 실측 시작값은 **4.9652** 임(부록.1 ① 참조).

> `0.35` / `0.10` 은 Windows 1개 환경 실측(0.0127 / 0.0025) 기준으로 **마진 27~40배를 확인해 유지**함.
> macOS·Colab 교차 검증은 해당 환경이 없어 수행하지 못했으므로 §6.3 완료조건에 미실행으로 남김.

#### L3 — 궤적 차분 검산 (GRU 판 "가장 주목한 토큰")

트랜스포머의 `가장 크게 주목한 질문 토큰: '먹구름이'` 에 대응하는 검산이 필요함. 어텐션이 없으므로 대체안을 비교함.

| 후보 | assert 가능? | 판정 이유 |
|------|-------------|----------|
| 게이트 `z` 히트맵 | ❌ 관찰용만 | 특정 시점의 게이트 최댓값 위치는 초기화에 좌우돼 불안정함 |
| 은닉 변화량 `‖h_t − h_{t−1}‖` | ❌ 관찰용만 | `h_0 = 0` 이라 **항상 t=0 이 최대**로 나오는 가짜 신호 |
| **궤적 차분 `‖h_t(먹구름) − h_t(별)‖`** | ✅ **채택** | 문장 틀이 동일하므로 t=0 은 비트 단위로 동일, t=1 에서 갈라짐이 수학적으로 보장됨 |

```python
assert torch.equal(hs_a[0, 0], hs_b[0, 0])   # 공통 토큰 '하늘에' 자리는 비트 동일
assert div[0].item() == 0.0                  # 차이가 정확히 0
assert div[1].item() > 1e-3                  # 대상 단어 자리에서 갈라짐
assert div.argmax().item() >= 1              # 최대 지점이 공통 토큰 자리가 아님
assert (div[1:] > 1e-4).all().item()         # 갈라진 차이가 이후 시점에서 사라지지 않음
```

이것이 이 실습의 핵심 훅임 — **어텐션 없이도, 답을 가르는 단어를 만난 그 순간 기억이 갈라짐.**

### 6.2 재현성 기준

**시드 고정만으로는 부족함.** `torch.manual_seed(42)` 는 난수 스트림만 고정하며, 값이 달라지는 지점이 4개 더 있음.

| 위험 지점 | 왜 깨지는가 | 대응 |
|----------|------------|------|
| **Linear 선언 순서** | 선언 순서대로 RNG 를 소비하므로 한 줄만 옮겨도 **모든 가중치가 달라짐** | `⚠️ 선언 순서 변경 금지` 주석 + 회귀 지문 비교로 감지 |
| BLAS 구현 차이 | x86(MKL) vs Apple Silicon(Accelerate) vs Colab 의 누적 순서 차이 → 연산당 `~1e-7` | 최종 loss 정확값 assert **금지** |
| 스레드 수 | 축약(reduction) 분할 방식이 스레드 수에 좌우됨 | `torch.set_num_threads(1)` 권장 (6쌍 배치라 속도 손실 없음) |
| torch 버전 | API 기본값 변경 | `weights_only` 를 명시적으로 전달 |

torch CPU RNG 는 플랫폼 독립이므로 **초기 가중치는 3플랫폼 비트 동일**함. 깨지는 것은 400에폭 누적 후의 값임.
즉 "L1 은 전 플랫폼 정확값 비교 가능, L2 최종 loss 는 불가"가 정확한 구분임.

#### assert 형태 결정 규칙

| 검증 대상 | 형태 | 정량 기준 |
|----------|------|----------|
| 파라미터 수, 단어장 크기, shape, 스텝 수, `<eos>` 위치 | `==` | 오차 허용 없음 |
| 동일 프로세스 내 재계산, 공통 접두 토큰의 은닉 | `torch.equal` | 차이 정확히 `0.0` |
| 직접 구현 vs `nn.GRUCell` 1스텝 / 5스텝 / 20스텝 | `allclose` | `1e-6` / `1e-5` / `1e-4` |
| 게이트 `r`·`z` 범위 | `>=` `<=` | `[0.0, 1.0]` |
| 후보 `n` 범위 | `>=` `<=` | `[-1.0, 1.0]` |
| 은닉 노름 | `<=` | `1.0 + 1e-6` |
| 강제 포화 게이트 항등성 | `allclose` | `atol=1e-8` (대수적 항등) |
| 1에폭 loss | 구간 | `2.0 < L < 3.6` (이론 2.890) |
| 최종 학습 loss / 평가 loss | **부등호만** | `< 0.35` / `< 0.10` (잠정) |
| 토큰 정확도 | `==` | `1.0` |
| 생성 답 문자열 | **집합 포함** | `ans in EXPECTED_ANSWERS` |
| 대조 답 구분 | 집합 크기 | `len(set(...)) == 6` |
| 갈라짐 최대 위치 | 부등호 | `argmax >= 1` (정확값 assert 금지) |
| 히트맵 픽셀 | **assert 금지** | 파일 존재 + `size > 10KB` 만 |

```bash
  && python mini_gru.py && python training.py && python reasoning.py \
```

```powershell
cd hands-on\gru
Remove-Item mini_gru.pt, gate_heatmap.png -ErrorAction SilentlyContinue
python mini_gru.py;  if (-not $?) { throw "L1 부품 실패" }
```

### 부록.1 계획 대비 정정 사항 2건

구현 과정에서 계획서의 전제가 틀렸음이 드러나 바로잡은 항목임. 원인과 조치를 남김.

**① 1에폭 loss 의 이론 기준값 (§6.1 L2)**

- 계획: `2.0 < L < 3.6` — 답 단어 18개 균등 추측 시 `ln(18) = 2.890` 이라는 근거
- 실측: **4.9652** 로 범위를 벗어나 `assert` 실패
- 원인: **가중치 공유**. 출력층이 `N(0,1)` 로 초기화된 임베딩 표를 그대로 쓰므로 시작 점수의
  분산이 커서(실측 logits std 1.72) 균등 추측보다 loss 가 높게 출발함.
  미니 트랜스포머도 같은 이유로 더 높게(측정 53.4) 출발함 — GRU 만의 문제가 아님
- 조치: 정답 정렬 검사는 `dec_in[:, 1:] == dec_tgt[:, :-1]` 가 **정확히** 담당하므로,
  1에폭 검사는 "폭발하지 않았는가" 가드로 격하하고 범위를 `1.0 < L < 8.0` 으로 정정.
  주석에 "이론값은 가중치 공유가 없을 때의 값"이라는 설명을 넣음

**② 갱신 게이트 `z` 최저 토큰 (§4.1 학습목표 2, §4.3 6단계)**

- 계획: `z` 가 가장 낮은 토큰이 `'먹구름이'` = 답을 가르는 단어
- 실측: 최저는 `'하늘에'`(0.447), `'먹구름이'` 는 두 번째(0.468)
- 원인: **첫 토큰은 회의록이 백지(`h=0`)에서 시작하므로 원래 `z` 가 낮음.** 빈 종이에 처음
  쓰는 것이니 "많이 고친다"가 당연한 것이며 그 단어가 중요해서가 아님.
  윤큐가 `‖h_t − h_{t−1}‖` 에 대해 지적한 "`h0=0` 때문에 t=0 이 항상 최대인 가짜 신호"와
  **같은 함정이 `z` 에도 있었음** — 계획 단계에서 놓친 부분
- 조치: 첫 토큰을 비교에서 제외하면 `'먹구름이'` 가 최저가 됨(0.468). 코드에서 `t≥1` 로
  제한하고 그 이유를 `⚠️` 주석으로 명시. 아울러 게이트 값은 **관찰용**으로 격하하고,
  검산의 주 증거는 궤적 차분(`assert` 가능, 실측 Δ=4.222 at t=1)으로 확정함

**③ 설정 불일치 시나리오 (§6.1 L4 의 E4, 엣지 케이스 EC-07)**

- 계획: "`hidden_size` 를 128로 바꾸고 재학습 없이 `reasoning.py` 실행 → 친절한 `RuntimeError`"
- 실측: **에러가 나지 않고 정상 동작함.** 재현 불가
- 원인: `reasoning.py` 는 `training.py` 의 상수를 읽지 않고 **체크포인트에 저장된 `config` 로**
  모델을 만듦. 즉 설정이 파일과 함께 움직이므로 애초에 불일치가 발생할 수 없음 —
  `config` 를 저장한 목적이 바로 이것이고, **에러가 안 나는 것이 설계 의도**임.
  계획 단계에서 "코드 상수 ↔ 체크포인트" 를 대조한다고 잘못 전제함
- 조치: 친절한 메시지가 실제로 필요한 조건은 **`mini_gru.py` 의 구조를 바꾸고 옛 체크포인트를
  읽는 경우**임(`state_dict` 모양 불일치). 저장된 가중치 한 개의 모양을 일부러 왜곡해 검증했고,
  의도한 안내 문구가 정상 출력됨. E4·EC-07 의 서술을 이 조건으로 정정함
